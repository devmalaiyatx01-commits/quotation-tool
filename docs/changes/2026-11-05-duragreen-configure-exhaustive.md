## Why

A designer picks Duragreen, Downlight in Add Product > Configure and looks for a Wall Wash beam. "75 Wall Wash" does not appear, though
Search shows it and labels it "Downlights - MOOD ROUND". They conclude the app cannot do it, or quote something else.

## Evidence

Read-only on the local database, 411 approved DuraGreen products:

- Through Configure's own endpoint, 6,686 of 6,686 values a product offers do reach its own typology's dropdown. So the options are right, and
  the gap is which products are in the pool.
- **Products under the wrong kind.** `75 Wall Wash` has beam `Wall Wash`, typology `Wall Grazer / Wall Washer`, category `Downlights - MOOD ROUND`.
  38 products have a category naming a different kind from their typology: 22 Downlights in Spotlight, 4 in Wall Grazer, 9 Track Lights elsewhere, and others.
  All 38 are DuraGreen; no other make has one.
- **Options that cannot be filtered.** Held by products but not asked in Configure: `baffle_finish` 97, `bezel_finish` 75, `version` 9.
- **One meaning, several spellings**, so picking one misses the rest: CRI `CRI 98` 139 and `98Ra` 57, `CRI 92` 6 and `92Ra` 107. Beam: 24 products list both `Zoomable 20°-50°` and
  `20°-50°`, and order codes use only the plain form. `120° Trimless` on 2 pendants. `92Ra with 97Ra option` is two values in one, as IP was.
- **Misread controls.** `55 Adjustable` lists `110` as its first control and `57 Straight Adjustable` lists `2 Step MacAdams`, the next column of the sheet. DuraGreen's own spec row names neither. Configure fills an unchosen control with the first option, so `55 Adjustable`'s default line said "DuraGreen prints no code". `Casambi Mini-Trim` (3 products) and `Casambi GLL-1` (1) are Casambi with a word run on.
- **Search reads names only.** It looks in name, category, series, family and variant, so `IP44`, `3000K` and `DALI` find nothing, and words must be adjacent.

## Scope

In:
- `app/typology_match.py` `category_kind`, `specsheet_summary` and `resolve_typology_options` in `app/main.py`, `static/app.js`: a product also appears under the kind its maker's category names.
- `app/duragreen.py` `configure_extras`: Configure also asks every other DuraGreen option the products hold.
- `app/duragreen.py` `spec_values`: one reading of CRI and beam, used by re-reads through `app/duragreen_sheet.py` and `app/duragreen_import.py`. `current_spellings`: a saved line's older spelling is read as what the product now lists. Misread controls are dropped or corrected there too.
- `scripts/backfills/backfill_duragreen_spec_values.py`: brings stored products in line, with `--dry-run` and `--undo`.
- `static/app.js`, `specsheet_summary`: Search looks in specifications, offered options and typology too, and matches each word wherever it is.
- `static/app.js`, for every make: a blank "Any" in the panel no longer wipes a choice in the product's own dropdowns; a reopened row's panel starts from what the row holds; a detail the panel asked reaches the line's `config` only if the product states that value.
- `app/main.py`: the Configure query reads three small columns of every approved product, then loads the matches in id order.

Out:
- `specsheets.typology` is not changed: Match, NPD and the Library keep today's classification. Match's rows still search one typology.
- Any price, order code, or BOQ line.
- Values whose meaning is the owner's call, listed in Next step.

## Design

Reuse the data already there rather than reclassifying. DuraGreen's own category says where it files a product, and typology says how the studio files it. A wall-wash downlight
is honestly both, so Configure offers it under both, and a designer looking either way finds it. Moving it would only hide it from whoever looks under the other.
The rule reads `category`, not a make, and `typology_key` already decides which names mean the same kind.

Rejected: changing `typology`, which moves the problem and touches Match. Equivalence at filter time, for spellings: the chosen value also reaches the product's form, so every
consumer would need the mapping. One stored spelling needs no mapping in what reads a product; `current_spellings` reads an older one in the one place a saved line is reopened.

## Risks

- A beam list going from two values to one makes it decided rather than a choice, which can change which code a line gets. Covered by A7.
- Code rows keep their own text, so renaming a value a row states would stop that row matching. None does locally: 0 rows state an old spelling and 0 are typed in. The backfill leaves any such product alone and lists it, for the live dry run. A re-read is not covered: a future sheet printing a CRI column "98Ra" on an uncut code would lose that match. No current row does this, and the audit CLAUDE.md requires after a re-read shows it as a round-trip failure, so it is left to that check.
- A BOQ line carrying an old spelling (locally 1 beam and 12 CRI values): reopened in Reconfigure, a value matching no option showed as "Any" and the next tweak filled in the first option, changing the line. `current_spellings` reads it as what the products in that selection now list. A value it cannot read still behaves as it always has.
- Under a kind that is not its typology, a product meets that typology's config rules. Locally 0 typology-wide rules exist and 0 rows name a DuraGreen product, so none applies; a rule added later would.
- The Configure query reads three small columns of every approved product before loading the matches, in id order, which fixes the dropdown's order for every make. Search loads `options` as well: see Budgets.
- A filter can narrow less than it looks: a product stating no value still lists, as it always has (no value is no constraint). Bezel Black goes from 163 products to 122. Such a product does not gain the value on its line, for any detail the panel asked. See Next step.
- A decided list in NPD replaces this: `configure_extras` applies only while nobody has decided for a typology, and `candidates()` reads the exact typology.
- An NPD tab left open across the data step and saved afterwards sends back the old values. Reload around the live run.
